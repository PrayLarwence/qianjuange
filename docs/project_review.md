# 项目评审

> 范围：项目作为一个整体的健康度。商业 / 战略 / 节奏 / 风险。  
> 视角：把项目当成一份资产看待，不只是一堆代码。

---

## 一、项目定位再确认

**一句话**：面向中文小说创作者的 AI 沙盒，能从既有手稿反向构建世界，也能从零推演新故事，最终导出小说章节。

**差异化卖点**（按独特性）
1. ⭐ **手稿反向构建（V1 + V2）** — 上传现有书 → 抽世界 → 续写。**市场上几乎没有竞品做到这点**
2. **多分支 what-if** — 一个事件分叉演两条线对比
3. **结构化叙事**（实体 / 事件 / 因果显式建模）— 不是"chat 出小说"，是"演出小说"

**不是什么**：
- 不是 ChatGPT 写作助手（那种只用对话）
- 不是网文 AI 续写器（那种只看文本）
- 不是世界设定编辑器（那种纯静态）

---

## 二、当前阶段判断

按软件项目典型生命周期：

```
点子期 → 原型期 → 闭环期 → 打磨期 → 推广期
                    ↑
                  我们在这
```

**已经做到**：
- 全部主功能模块都有原型
- 后端 21k 行有测试
- 前端有两套实现（虽然是债）
- 9 个月持续投入

**还没做到**：
- 没有任何作者完整用它写过一本书
- 没有用户反馈闭环
- 没有公开发布
- 没有可分享的"看一眼就懂"的 demo 或视频

**这是典型的"功能宽，实战窄"的状态**。技术在前进，价值验证落后。

## 三、做得好的地方

### 1. 工程素养在线（个人项目少见）
- 115+ pytest，FakeProvider 替身，2.5 秒跑完
- 数据模型不是事后凑的，分支 / 因果 / 实体快照都是早期就考虑的
- Provider 抽象做得干净
- README 写得清楚（这次重写后）
- TaskCreate 用得勤，进度可追

### 2. 技术选择保守而正确
- SQLite 而不是上来就 Postgres：单机工具不需要
- FastAPI + Vue 3：标准栈，不引野怪
- vis-timeline / cytoscape：可视化用成熟库
- 自己抽 Provider 而不是依赖某家 SDK：避免锁定

### 3. 创新点真的有
- 把"小说"建模成"事件 + 因果 + 实体快照"这件事，**比让 LLM chat 出一本书更接近"可控创作"的本质**
- 手稿反向构建是真创新
- 角色 sub-agent + 导演的多 agent 模式有探索价值

### 4. 节奏感好
- T2 / T3 这两批改动单次都聚焦，没有一次性爆改
- 每次都做 build + 语法检查
- handoff 文档及时

## 四、做得不好的地方

### 1. 缺一个真实用户（哪怕就是作者本人）
- 9 个月没有人用它写完过一本书
- 所有功能优先级靠推测
- T2 / T3 的需求颗粒度都没经过实战验证
- **这是项目最大风险**

### 2. 广度优先于深度
- 模板系统、程序化地图、并发探索、persona 萃取、关系图谱、POV 改写、文风模板、一致性扫描、手稿反向构建、多 agent 推演 — **每一个都是别人能做半年的功能**
- 但每一个都停在"能跑"，没到"好用"
- **没有一个功能是可以拿出去说"这块我们做到行业最好"**的

### 3. 方向感不稳
- T1 / T2 / T3 的具体内容上次说了没存到 memory，今天回来要重对
- 路线图列了 3 条但没有"主轴"
- 容易被新点子带偏

### 4. 没有反馈机制
- 没有 metrics（不知道钱花哪 / token 怎么用 / 哪个工具最常被调）
- 没有错误监控（LLM 失败只能 stderr 看）
- 没有用户留存数据（连作者自己用了几次都没记录）
- **盲目飞行**

### 5. 对外发布度为零
- 没有 demo 视频
- 没有公开仓库（git is_repo=false）
- 没有 landing page
- 没有跟其他类似工具的对比

## 五、机会与威胁

### 机会
1. **市场空白**：中文创作者 + 多分支推演 + 手稿反向构建，三个交集没有产品
2. **网文作家市场**：起点 / 番茄养着百万作者，他们对"一致性 / 伏笔 / 人物 OOC"的痛是真实的
3. **LLM 价格在跌**：DeepSeek、本地模型都让 token 成本降到能负担的水平
4. **AI 写作工具市场升温**：业界投资在涌进，先发优势有窗口

### 威胁
1. **大厂下场**：Notion / Cursor / 文心 / 豆包 任何一家做"故事工坊"产品都能用资源碾压
2. **作者拒绝 AI 风潮**：起点已经有"反 AI 创作"运动，目标用户里相当一部分情绪化抵触
3. **个人维护极限**：40k 行已经接近单人能持续投入的上限
4. **LLM 输出不稳定**：模型升级 / 降级会让产品质量上下波动，不可控

## 七、关键决策点

下一阶段必须做的决策（按重要性）：

### 决策 1：项目目的到底是什么？
- A. 个人工具（自己写小说用）→ 那现在功能严重过剩
- B. 开源副业（GitHub 几千星的小工具）→ 那要做发布、做演示、写文档
- C. 创业项目（要找用户、做留存、想商业模式）→ 那当前状态还非常早，需要深度
- **明确了 A/B/C 才知道下一步往哪走**

### 决策 2：广度还是深度？
- 继续加功能（T1 一致性、并发探索升级、多 agent 深化）
- 还是停止加新功能，把手稿 → 续写 → 导出这条线打到能用？
- **建议：深度。理由：广度收益递减，深度能产生真实反馈**

### 决策 3：作者是不是"自己的第一个用户"？
- 是 → 立刻找一本想写的小说，从今天开始用这个工具写
- 否 → 那这个项目就是个技术练习品，不要再投入
- **这个决策无法回避**

### 决策 4：双前端怎么处理？
- 立刻冻结老版
- 给定 1 个月让 next 追平
- 1.5 个月后删除老版
- **拖越久越痛**

### 决策 5：要不要公开？
- 不公开 → 永远没用户反馈 → 项目无法验证
- 公开 → 要面对 issues / PR / 解释 / 维护
- **可以"半公开"：先开源不推广，给少数人看**

## 八、下一阶段建议路线图

### Phase A（接下来 2 周）：闭环
1. 作者自选一本 50-100k 字小说（自己写的或想续写的）
2. 完整跑：手稿导入 → 抽事件 → 审阅 → 续写 5-10 章 → 导出
3. **真实记录踩到的坑**：每一个不顺手的地方写到 issue list
4. 这个过程**不写新功能**，只 fix 阻断性 bug

### Phase B（接下来 1 月）：打磨
1. 按 issue list 排优先级
2. 拆 `routes.py` + 拆 `WorldSettingsView`
3. 加 metrics
4. 老 `frontend/` 冻结公告

### Phase C（再 1-2 月）：发布
1. 录 5 分钟 demo 视频
2. 写一篇"我用 AI 沙盒续写《XXX》前 10 章"的实战博客
3. 开源（不推广，挂上去先）
4. 找 5-10 个真实写作者朋友试用，收反馈

### 不要做（接下来 3 月内）
- 不要加任何新功能模块
- 不要做地图深度联动
- 不要做并发探索 UI 升级
- 不要做新 Provider 接入

## 十、结论

这是一个**技术上扎实、产品上模糊**的项目。

**资产层面**：
- 18 张表的数据模型 + 30 个 engine 模块 + 115 条测试 + 多 Provider 支持，这些是真实资产
- 手稿反向构建是真正的差异化，**这是核心资产**

**负债层面**：
- 4000 行单文件、双前端、零可观测性，这些是工程债
- 0 真实用户、无方向主轴、不公开，这些是产品债

**关键判断**：
- **工程债是机械问题，可解**
- **产品债是认知问题，必须先回答"我做这个给谁用"**

**给作者的话**：
你写了一个能让 AI 帮你写小说的工具。下一步不是教 AI 写得更好，是先用它给自己写一本你想看的小说。它会告诉你下一步该做什么。
