# 需求评审

> 范围：把当前已实现 + 路线图上的功能，按「用户故事 → 价值 → 完成度 → 取舍建议」过一遍。  
> 视角：把作者本人当成第一用户。

---

## 一、目标用户与核心场景

**目标用户（按优先级）**
1. 想在已有小说基础上做「续写 / what-if 改写」的创作者（手稿反向构建是项目的差异化卖点）
2. 想用 AI 辅助原创长篇但担心人物 / 时空 / 因果失控的网文 / 长篇作者
3. 把"故事工坊"当成创意拼盘的玩家用户（输入种子设定 → 看 AI 怎么演）

**核心场景**
- **场景 A（手稿续写）**：上传现有小说 → 抽骨架 + 事件 → 审阅 → 在原书结尾继续推演 → 导出新章节
- **场景 B（原创推演）**：选模板 / 空白世界 → 推 N 步 → 分叉做 what-if → 导出小说
- **场景 C（写作辅助）**：自己写章节，用一致性扫描查 OOC / 时空矛盾、用 persona 萃取查角色一致性

## 二、功能模块梳理

### 模块 1：手稿反向构建（V1 + V2）⭐ 项目灵魂
| 项 | 状态 | 完成度 | 备注 |
|---|---|---|---|
| V1 章节切分 | ✅ | 100% | 中文 / Markdown / 空行三种策略 |
| V1 LLM 抽骨架（cast / outline / locations / factions） | ✅ | 90% | T2-A 改成分批后能吃长小说 |
| V1 角色别名识别 | ✅ | 70% | T2-B 落地，识别率取决于模型 |
| V2 事件抽取（按章节） | ✅ | 95% | T3-B 支持范围抽取、T3-C 中途持久化 |
| V2 名字解析（含 aliases） | ✅ | 80% | 还有不少 unresolved 名字 |
| V2 因果链抽取 | ✅ | 70% | T2-C 落地，跨度 > 80 tick 会漏 |
| 审阅 UI（编辑 participants / location） | ✅ | 90% | T2-D 新增 |
| 端到端真实小说测试 | ❌ | 0% | **最大空缺** |
| V1 转异步 job | ❌ | 0% | 长小说会超时，下次需要 |
| 抽小说世界规则 / 设定（不只 setting 字段） | ❌ | 0% | 现在只有一段散文 setting |

**评价**：这是项目最独特的能力，市面上几乎没有。但**没经过真实使用验证**，T2/T3 的工作大量基于推测式需求。

## 三、需求合理性追问

### Q1：双前端（frontend / frontend-next）值得保留吗？
现状：Alpine 老版 12k 行，新版 Vue 6.8k 行。**长期维护两套是负担**。

建议：
- 明确老版进入冻结，新功能只进 next
- 或者直接在 README 标"frontend-next 是主线"，老版 6 个月内删

### Q2：地图模块投入产出比？
现状：地图 + 移动 + 程序化生成做了一整套，但和"小说创作"主线的连接弱。

追问：
- 你写的小说多大比例需要 2D 地图？
- 如果是「都市 / 校园 / 仙侠（场景为主）」类型，地图模拟的实用价值多高？
- 这块能不能降到「可选插件」的优先级？

### Q3：并发探索 / 多分支 what-if 的真实使用频率？
现状：能力齐了，UI 暴露弱。

追问：
- 你自己写作时会真的去对比 3 个分支选最好的那个吗？
- 还是说大多数时候只用主线？
- 如果是后者，多分支的复杂度（branch_id 处处带、合并逻辑等）是否成本过高？

### Q4：「一致性扫描」是个实用功能还是个 demo？
现状：能扫出问题，但用户拿到结果后下一步动作不清晰。

追问：
- 扫出 50 个 issue 后，用户怎么处理？逐条点开？
- 应该有「按角色分组 / 按 tick 范围过滤 / 按严重度排序」这些 UX 改进
- 「采纳 patch」这个动作目前怎么落库？是改原事件还是写新事件？

## 四、需求空缺（已识别但未做）

### 高价值空缺
1. **真实使用闭环**：作者本人完整跑一遍 100k 字小说的导入 → 续写 → 导出。这能暴露的问题比再加 3 个功能都多
2. **一致性结果 UX**：分组、过滤、跳转、批量操作。这是把「能扫」升级到「能用」的关键
3. **手稿世界规则抽取**：现在只有一段散文 `setting`。应该尝试抽出结构化规则（"内功修为分九级"、"修真者寿命 300"），写到 World.rules 里
4. **PlotThread 自动跟进**：每次 advance 后扫描长期未推进的线索，生成 reminder
5. **导出 docx / epub**：作家投稿、上传起点都需要

### 低价值或可暂缓
1. 地图深度联动（如果不写场景类小说）
2. 角色情绪曲线深化（视觉化已经够，再深没人看）
3. 程序化地图新算法

### 不确定但值得探索
1. **写作"辅助 hover"**：阅读视图悬停某段散文 → 显示底层事件 / 涉及实体 / 因果链
2. **LLM 自检模式**：每次 advance 完，让 LLM 自己反查"这一步有没有违反 persona / 时空 / 已有因果"
3. **协作模式**：两个 AI 同时驱动两个角色，看会演出什么
4. **章节产出预览**：不导出整本，只看下一章会写成什么样

## 五、需求优先级建议（下一阶段）

按"独特价值 × 完成度差距 × 实施成本"排：

| 优先级 | 需求 | 理由 |
|---|---|---|
| **P0** | 作者亲自跑通真小说全流程 | 唯一能验证 T2 / T3 的方式，**这一步不做后续都是空中楼阁** |
| **P0** | 一致性结果 UX（分组 / 过滤 / 跳转 / 一键忽略） | 把现有能力变得可用 |
| **P1** | V1 转异步 job | 长小说会超时，是真小说测试的拦路虎 |
| **P1** | 手稿世界规则结构化抽取 | 续写质量的关键，现在 setting 散文 LLM 看不懂 |
| **P1** | PlotThread 自动跟进 | 长篇连贯性的核心 |
| **P2** | 导出 docx / epub | 实用，但简单 |
| **P2** | 写作 hover（散文 → 底层事件） | 增强可读性 |
| **P3** | 老 frontend 冻结公告 + 删除计划 | 减债 |
| **P3** | routes.py 拆分 | 工程债 |
| **冻结** | 地图深度功能、并发探索 UI、角色弧光二期 | 在主流程跑通前不再投入 |

## 六、风险

1. **没有真实用户反馈**：所有 Tier 分类、所有功能优先级都基于推测。开发了 9 个月没人用过完整流程，这是项目最大风险
2. **方向漂移**：T1 / T2 / T3 的具体定义没存到 memory，每次回来要重新对齐
3. **双前端 + 4000 行 routes**：再做 3 个月会进入「改一个小功能要碰 5 个文件」的状态
4. **AI 调用成本**：长小说 V1 + V2 + 因果链可能是 3-5 美刀级别的单次调用，目前没有成本提示 / 预估
5. **LLM 输出不稳定**：aliases、因果识别、一致性判断都依赖 LLM 配合，没有准确率监控

---

## 七、结论

项目的需求侧已经过度宽泛。核心能力都铺开了但都没深耕过。**下一阶段的本质问题不是"加什么功能"，而是"把哪条线打透"**。

最低风险路径是聚焦手稿反向构建 + 续写这一条线，把它变成作者自己的日常工具。一致性扫描、persona、并发探索这些放二线，等核心闭环跑顺再回来。
